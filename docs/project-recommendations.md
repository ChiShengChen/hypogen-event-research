# 專案建議：定位、評測、工程與路線

2026-11-23。依據為 README 所列的 benchmark 結果、目前的程式碼，以及[文獻綜述](literature-review/README.md)（44 篇論文，341 張逐字驗證的證據卡）。文中引用的文獻數字都可在綜述裡依卡片編號查到原文。

## 摘要

1. **「比純模型更準」是核心賣點，但目前的證據還撐不起來。**以同一個 Astra 比較，數字題大多打平或落後；領先多出現在評分表檢查的結構項目。文獻顯示這個主張可以成立，前提是選對題型，並用確定性評分或前瞻實績來證明（§2）。
2. **歷史回放只能驗證流程，不能證明預測能力。**`as_of` 提示、匿名化與搜尋日期過濾都擋不住模型記憶。
3. **最弱的一環是評審。**Sol 與 Astra 同屬 GPT-6.2 家族，人工評分 0 案，前瞻實績也是 0 案。
4. **小樣本加反覆改版，結論容易被雜訊左右。**8 案的保留集即使打平或領先兩案，統計上都分不出差異。
5. **建議把資源從「再做一版 benchmark」移到三件事：有機會贏的題型、人工與前瞻評分、來源原文保存。**後兩項也是準確度主張能被採信的前提。

## 2. 產品定位：讓「比純模型更準」站得住

**「比純模型更準」是研究員最直接的採用理由，應保留為核心主張。**問題不在方向，而在目前選的題型和證明方式。

### 2.1 Harness 難贏的題型

在前沿模型上，「讀文件、算出單一數字」的題目，準確度主要取決於模型本身和資料取得，harness 很難拉開差距：

- EPSBench 換 harness 只讓 EPS 誤差變動 −0.004 到 +0.001；
- FinDeepForecast 的專門 agent 只比內建搜尋的前沿模型高 3-4 個百分點；
- kw-bench 在前沿模型上 harness 差異消失（0.9986 對 1.000）。

本專案的盈利 MAE、第二預測季營收、指引驗證器都屬於這一類，結果也一致。

### 2.2 文獻中 harness 確實更準的條件

| 條件 | 文獻證據 | 本專案可對應的題型 |
|---|---|---|
| 純模型有系統性錯誤，可用確定性程式碼修正 | Frontier Financial Judgement：所有前沿 agent 都跟著年增的利多標題走，沒有算出隱含的季度下修。銀行合規研究：算術類規則應交給確定性程式碼 | 季度指引修正、單位與倍率、EPS 對帳、跨季認列 |
| 需要純模型拿不到的資料或工具 | FinDeepForecast：同一模型拿掉搜尋，準確率掉 11.0 到 14.2 個百分點。FrontierFinance：Opus 4.8 只用網搜 33.0，接上金融工具 harness 45.0。FinSkillBench：整理好的領域技能把分數從 0.366 提高到 0.528，增益集中在計算密集的投組與風險任務 | SEC 結構化資料、授權共識、計算工具 |
| 時點正確本身就是答案的一部分 | BuySideFlow：答案正確的執行有 50.8% 仍違反時點規則；把時點規範加進 agent 後，結果準確率從 44% 升到 55% | 「截止時點當下能知道什麼、能算出什麼」類題目 |
| 模型越弱，harness 幫得越多 | kw-bench：便宜模型上兩種 harness 分別得 0.542 與 0.528，另兩種得 0.00。投行簡報研究：27B 加 harness 和直接用 Opus 打平（−4.7 到 +0.8）。FinSkillBench：gpt-4.1 增益 +0.405，gpt-5.4 只有 +0.091 | 較小、較便宜的模型加 harness，達到 Astra 的準確度 |

### 2.3 建議

1. **主戰場改到上表前三類**，不在「讀公告、填一個數字」的題型上反覆調提示。
2. **準確度只用確定性評分或前瞻實績來證明，不用 LLM 評審。**每組至少重跑 3 次，案數依檢定力決定（§3.5）。
3. **加一個次要主張：同等準確度、成本更低。**用較小模型加 harness 對上 Astra，這是文獻中 harness 最常見的勝場。
4. **流程價值是「更準」的可信度來源，不是替代品。**研究員能沿著引文和財務橋接自己驗證，才會相信「更準」不是運氣或記憶。純模型給不了這種保證：Finance Agent Benchmark 要求附引用，卻沒有檢查引用是否正確。

準確度主張需要搭配以下指標，一起報告：

| 指標 | 意義 | 目前狀態 |
|---|---|---|
| 準確度（主指標） | 對比純 Astra 的答對率或誤差，限確定性評分或前瞻結果，附信賴區間 | 多為歷史回放或 LLM 評審 |
| 引文有效率 | 引文確實支持所述事實的比例，以原文為準 | 只驗證 ID 與期限，未驗證語義 |
| 時點違規率 | 讀取了截止時點後才可得資料的比例，以執行軌跡為準 | 部分；網路來源依模型回報的日期判斷 |
| 重算一致性 | 同輸入重算結果完全一致 | 已具備 |
| 研究員覆核時間 | 從拿到報告到確認或推翻主張所需時間 | 盈利類覆核表有欄位，假說類沒有；0 案 |
| 錯誤被發現率 | 研究員能否靠引文與財務橋接找出錯誤 | 未測 |

## 3. 評測方法

### 3.1 分開「流程驗證」與「預測能力」

- 歷史回放的結果，在文件與 README 中標為「流程驗證」。它能證明時點過濾、引文和計算有正確運作，但不能證明模型會預測。
- 預測能力的結論只用兩種資料：模型訓練截止後的事件，或前瞻佇列。The Memorization Problem 的作者指出，截止點前取大樣本、截止點後取小樣本當穩健性檢查，在方法上無效。

### 3.2 回放案例的洩漏檢查

在宣稱回放結果之前，逐案跑以下檢查：

1. **記憶探針**：只給 ticker 與日期，請模型猜財報方向或指引落點。若準確率明顯高於隨機，該批結果視為受記憶污染。有一篇研究用這種探針，在截止前測到 59.2%、截止後 53.3%。
2. **擾動測試**：把證據中的關鍵數字改掉，看預測有沒有跟著變。預測不變，代表模型沒有在讀證據。
3. **不要用前後截止比較當洩漏檢查。**Temporal Leakage in LLM Backtesting 指出，在全部題目都晚於截止點的情況下，這種比較仍會誤判有洩漏。要量化洩漏時，用已知截止點的斷點，或匹配的對照模型。
4. **不要依賴 `as_of` 提示或匿名化。**叫 GPT-4o 忽略 2010 年後的資訊，準確率仍是 97.6% 對 98.0%，真正截止後只有 40%。遮名後的財報電話會議逐字稿，模型仍認得出公司。

### 3.3 評審

目前的設定是 [hypothesis_pilot.py](../benchmarks/hypothesis_pilot.py) 中 `JUDGE = "gpt-6.2-sol"`，產生模型是 `gpt-6.2-astra`，兩者同一家族。文獻中的風險：

- 同家族同系列的評審有約 8.9% 的偏好洩漏，換成不同系列降到 2.8%；
- 同家族評審彼此高度一致，不是獨立評分者；
- 改提示措辭會翻轉四分之一到三分之一的系統比較判決；
- 交換順序能揭露、但不能消除位置偏誤。

建議：

1. **改成跨供應商的三評審多數決**（FrontierFinance 的做法），並固定評審設定與版本。
2. **先測評審本身的穩定度再用它。**同一批配對做三組重評：每種順序重評 3 次、2 種提示措辭、5 天後再評一次。報告判決翻轉率。翻轉率高於兩組系統的分差時，該分差不採計。
3. **把評審限縮在可查核的維度**，例如證據是否支持、因果鏈是否完整、預測是否有指標與期限。原創性、重要性等判斷交給人。金融論文審稿研究發現，GPT-4o 只有正確性與表達的評分有預測力。
4. **用人工標註校準評審**，不要只靠提示叫它公正。在偏好洩漏研究中，「要求公正」沒有效果（18.3 對基準 17.8），用保留的人工標註做校準降到 7.3。

### 3.4 人工評分

這是目前效益最高的投入。覆核包、匿名對照鍵與空白評分表都已經有了，缺的是評分者。

- **起步**：linkage-depth 12 案、V9 限流後復原 4 案、V9 四案 4 案，合計 20 個配對，請 3 位具財務背景的分析師各自評分。
- **目標**：依 Alternative Annotator Test 的做法，至少 3 位專家評 50 到 100 份，各評分維度分開檢定，容許差距 ε 取 0.2。通過的維度才可用 Sol 取代人工。
- **預期**：LLM 評審不比被評模型強時，最多只能把所需人工標註減少一半。人工評分不能省略，只能減量。
- **一併記錄覆核時間**，作為 §2 的研究員覆核時間指標。
- 評分者要找金融背景的人。在財經評論研究中，LLM 評審與人類的逐項一致率只有 27.2%，金融專家的首選模型沒有拿到任何 LLM 評審的票。

### 3.5 樣本量與重跑

- **8 案的保留集分不出差異。**以配對的對錯結果做精確 McNemar 檢定：8 案中至少要有 6 案是「一方對、一方錯」且全部偏向同一方，雙尾 p 才會低於 0.05（6 案全偏一方時 p = 0.03125，5 案時 0.0625）。V10 保留集的不一致配對是 2 對 2，p = 1。
- **事先算檢定力，再決定案數。**預註冊時寫下最小可偵測差異；達不到就說明這輪只能檢查流程。
- **每個設定至少跑 3 次**，報告同案重跑的離散。EPSBench 正是這樣做，它的同案重跑離散（0.057）大於 harness 造成的差異。另一篇研究中，同一 agent 七次執行通過的 rubric 條目在 149 項中介於 105 到 123。
- 結論附信賴區間。區間跨零時寫「無法分辨」，不寫「打平」。

### 3.6 前瞻評測改為主指標

- **擴大財報前瞻佇列。**目前 5 家公司各 6 案，已封存 3 案。每季財報季有大量事件，可擴到每季至少 30 案，並用固定容差做確定性評分。FinDeepForecast 的容差是：百萬級財務數字 5%、比率 1%、利率與匯率 0.1%。
- **假說到期自動核對。**報告裡的「可查核預測」已經寫明指標、方向、公開來源與截止日，正好可以到期後自動核對，產生真實結果分數。這對應 [plan.md](../plan.md) 原本規劃的 `POST /hypotheses/{id}/outcomes`。HindSight 的結果顯示，結果分數和評審分數可能完全相反：評審給 7.44 對 7.40，結果分數是 0.297 對 0.119。
- **用虛構事件評估假說。**仿照 Frontier Financial Judgement：由分析師撰寫合理但虛構的事件，混入真實新聞，用專家標籤做確定性評分。這樣可以完全避開記憶與搜尋洩漏。

## 4. 工程與資料

### 4.1 網路來源的可得時點與原文

[discovery.py](../research_app/discovery.py) 有兩個問題：

- **可得時點來自模型。**`Candidate.published_on` 是模型在搜尋結果中回報的日期，`historical_replay` 再以該日的 UTC 日末作為可得時點。
- **證據文字是模型摘要。**來源段落以 `text_format="summary"` 保存，所以引文檢查比對的是模型自己的摘要，不是原文。

文獻的相關發現：搜尋日期過濾在 Google 有 71.0% 的題目、DuckDuckGo 有 81.2% 撈到截止後的重大資訊；頁面標示的更新日期也不可靠。

建議：

1. 抓取並保存原始頁面（HTML 或 PDF），記錄雜湊與抓取時間；引文改為比對原文。
2. 可得時點改用可驗證的來源：SEC 用 EDGAR 的受理時間；公司 IR 頁面用網頁存檔的擷取時間。沒有可驗證時間的來源，標為「時點未驗證」，不納入預測能力評測。
3. `historical_replay` 產出的報告，在 JSON 與 Markdown 中都標示「不適用於預測能力評估」。

### 4.2 SEC 財務資料：保持現行做法

[earnings_cases.py](../benchmarks/earnings_cases.py) 對每個期間採用最早申報的值，也就是首次揭露的數字，可以避免日後重述污染回放（文獻舉的例子是 Enron 在 2002 年改寫 1998-2001 的盈餘）。這點是對的，建議在測試中鎖定這個行為。

### 4.3 在讀取時強制時點，而不是事後檢查輸出

BuySideFlow 的規則式檢查器只抓到 34.9% 的違規；最常見的錯誤是把報告期間當成公開日期。建議：

- 每次讀取文件，都記錄文件 ID、可得時點與截止時點，並在讀取當下拒絕不合格的文件；
- 評測時稽核整條執行軌跡，不只看最終輸出；
- 財報類資料一律分開保存「期間結束日」與「公開日」，在 schema 層禁止混用。

### 4.4 數字題交給確定性程式碼

銀行合規研究也建議，算術類規則用 harness 中的確定性程式碼處理，而不是再加一次模型呼叫。本專案的 Decimal 財務橋接方向正確，可以延伸到：

- **季度指引修正的算術。**Frontier Financial Judgement 中，所有前沿 agent 都跟著年增的利多標題走，沒有算出隱含的季度下修。這是 Harness 有機會用確定性評分證明領先的題型。
- **表格單位與倍率解析。**改用明確的解析流程，無法確定時暫緩，並把「暫緩是否正確」當成一個指標。目前的做法是逐案加規則（見 §5）。

### 4.5 整合 benchmark 程式

`benchmarks/` 已超過 35 支腳本，封存、先導、保留集、執行帳本、限流復原、覆核包與報告的邏輯一再重複。建議抽出一個共用評測框架，各實驗只寫案例與評分規則。好處：

- 試驗帳本自動累計（見 §5）；
- 協定差異一目了然；
- 新實驗的成本下降，人力可以轉到人工評分與前瞻核對。

### 4.6 成本與延遲

公開題庫中，Harness 18 個搜尋案有 16 案超過提示預算，T3 中位耗時 224.5 秒，純 Astra 是 51.3 秒。建議二選一：設定硬預算再做等預算比較；或明確定位為離線研究工具，不和即時問答比速度。

## 5. 研究流程與迭代紀律

- **每個版本都算一次試驗。**V8、V9、V10，以及每次驗證器修改，只要在先導集上評過分就計入帳本，報告時寫出總試驗數。Hard to Fool 的研究迴圈裡，一個發現期與驗證期 Sharpe 接近 3 的規則，在保留集掉到 0.26。
- **保留集只開一次。**沒過就換新的保留集，不在同一批上修改後重跑。目前每輪都換新發行人，做法正確，應寫進協定。
- **分開結構性修改與個案規則。**在 Can You Trust Your Finance Agent? 中，結構性修改能推廣到新題目，依開發題寫的個案規則則不能：開發集的 +14 到了保留題只剩 +1.5。驗證器逐案補規則（複數 `revenues`、多層表頭、左欄單位）屬於後者，預期推廣性差。
- **每條賽道事先寫下停損條件。**例如：前瞻佇列累積 30 案後，若 EPS 誤差仍未低於純 Astra，就把該賽道的準確度主張收起來，相關功能維持選用，人力轉到 §2.2 較有機會的題型。目前「未達門檻即列為選用方案」的做法是對的，可以再明確寫出何時整條賽道收尾。

## 6. 準確度以外，值得一起量的差異

| 方向 | 依據 | 建議的評測方式 |
|---|---|---|
| 證據不足時保留判斷 | V10 負例 4/4 對 2/4，但正例 2/4 對 4/4 | 改用精確率、召回率與棄答率，畫出取捨曲線，不只看全對數。少說錯也是「更準」的一種 |
| 長流程中的時點違規 | 結果正確的執行約一半仍違規 | 執行軌跡稽核，比較 Harness 與純 Astra 的違規率 |
| 研究員工作流程 | 這是產品真正的使用情境 | 研究員分別用工作台與純 Astra 對話完成同一題，比較覆核時間與找到的錯誤數 |
| 情境重算 | 3.78 毫秒、無模型呼叫 | 與純模型逐次重問，比較一致性與成本 |

## 9. 建議停止或降低優先的事

- 用「歷史回放加 LLM 評審」來證明準確度勝過 Astra。這種設定下，即使領先也無法被採信。
- 在「讀公告、填一個數字」的題型上反覆調提示追準確度。
- 逐案替驗證器新增規則。
- 用 8 案以內的領先門檻判定優劣。
- 用單一同家族評審的分數作為主要結論。
- 在人工評分到位之前，繼續新增評審評分的 benchmark 變體。
